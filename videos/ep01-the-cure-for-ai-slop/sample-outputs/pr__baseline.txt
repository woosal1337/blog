## Add retry-with-backoff to HTTP client and fix connection pool leak

### Summary

Adds automatic retry with exponential backoff to the HTTP client for transient failures, and fixes a connection leak in the pool where failed or timed-out requests were not releasing their connection back to the pool.

### Problem

- Requests that failed with transient errors (timeouts, connection resets, 5xx responses) were surfaced immediately to callers with no retry, forcing every call site to implement its own ad-hoc retry logic.
- Under sustained load or upstream instability, the connection pool would gradually exhaust its available connections. The root cause: error and timeout paths in the request lifecycle returned early without releasing the checked-out connection, so it stayed marked "in use" indefinitely. Over time this starved the pool and caused unrelated requests to hang or fail with `pool exhausted` errors.

### Changes

- **Retry with backoff**
  - Wraps outgoing requests in a retry policy with exponential backoff and jitter.
  - Retries only on idempotent methods and a defined set of transient failures (connection errors, timeouts, configurable 5xx status codes); non-idempotent methods and 4xx responses are not retried by default.
  - Backoff parameters (max attempts, base delay, max delay, jitter) are configurable, with sane defaults.
  - Respects `Retry-After` headers when present.

- **Connection pool leak fix**
  - Ensures the connection is always released back to the pool via a `finally`/cleanup path, regardless of whether the request succeeds, errors, or times out.
  - Adds a guard so a connection can't be double-released or leased twice.

### Testing

- Unit tests covering: retry on transient errors, no retry on non-idempotent/4xx, backoff timing and jitter bounds, and `Retry-After` handling.
- Regression test that drives repeated failing requests through the pool and asserts pool size/available-connection count returns to baseline afterward (previously would leak and eventually deadlock).
- Manual verification against a flaky upstream (simulated with random 5xx/timeout injection) to confirm no connection exhaustion under load.

### Risk / rollout notes

- Retry behavior is opt-in-by-default but configurable; callers with strict latency budgets should review the new default max-attempts/backoff ceiling.
- No public API breaking changes — new options have defaults matching prior (no-retry) behavior for total request count, only the leak fix changes runtime behavior, which is strictly corrective.
